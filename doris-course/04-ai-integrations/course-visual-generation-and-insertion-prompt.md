# Course 配图生成与插入 Prompt

下面的 Prompt 用于继续为其他 Module 的 Course Markdown 设计、生成并插入教学配图。它总结了 `real-time-analytics / level-1 / module-1` 已验证合格的选图、画面内容、视觉形式和 Markdown 插入方式。

## 可直接使用的 Prompt

```text
你正在为 VeloDB / Apache Doris 英文课程制作教学配图。

目标 Course Markdown：
<COURSE_MD_PATH>

Module 标识：
<MODULE_ID>

请完整阅读目标 Markdown，再完成“分析选点 → 生成图片 → 插入 Markdown → 检查”的全过程。不要只根据标题猜测课程内容，也不要改写课程中与配图无关的正文。

一、先确定配图位置

1. 从用户学习路径出发，选择 3–5 个最值得图示化的位置；内容较短时可以少于 5 张，不要为了凑数量插图。
2. 优先选择以下类型的内容：
   - 初次出现、仅靠文字不容易建立心智模型的核心概念；
   - 数据、查询或控制信号经过多个组件的流程；
   - Apache Doris 在系统或数据链路中的位置；
   - FE、BE、存储、客户端、外部系统之间的职责关系；
   - 两种或多种架构、执行方式、设计选择的对比；
   - 数据从写入、组织、执行到结果返回的阶段变化；
   - 当前以 ASCII / text 代码块表达、实际更适合流程图的内容。
3. 不要为普通定义、简单列表、单条 SQL、纯操作步骤或相邻内容已经充分解释的段落重复配图。
4. 每张图片只能承担一个明确的教学任务。图片应帮助用户回答“数据在哪里、谁负责什么、下一步发生什么、两种方案差在哪里”中的一个主要问题。
5. 在生成前列出简短计划，包含：
   - 插入锚点：放在哪一段或哪个小节之后；
   - 图片主题；
   - 图片中的组件和箭头关系；
   - 图片对该段内容的说明作用；
   - 建议文件名和画面比例。
6. 图中的事实、组件名称和箭头方向必须能从课程正文得到支持。不要添加正文没有讲到的产品能力、性能数字、部署组件或因果关系。

二、统一视觉风格

所有图片必须与 VeloDB Website 首页的深色技术流程图保持同一视觉语言：克制、清晰、工程化，而不是营销海报或通用 AI 插画。

强制要求：

- 背景使用纯黑色，不使用纹理、照片、网格背景、渐变背景或装饰性光斑。
- 所有涉及 Apache Doris 的核心节点统一画成纯色深蓝矩形块。
- Doris 深蓝块中只写 `APACHE DORIS`，不要放 Apache Doris Logo，不要写 `VELODB ENGINE`，也不要附加其他 Logo。
- Doris 深蓝块不要使用渐变、玻璃效果、立体透视或复杂纹理。
- 其他系统、数据源、客户端、表、节点和结果使用黑色或极深灰色卡片、细描边和简洁线性图标。
- 主流程箭头和关键连接使用 VeloDB 电蓝色；次要边框使用低对比度蓝灰色。
- 主文字使用白色或接近白色；辅助说明使用冷灰色；少量关键词可以使用蓝色强调。
- 使用二维正视图，不使用 3D、等距透视、人物插画、拟物设备或照片。
- 边框细、圆角轻微、留白充足。不要使用大面积阴影、发光、霓虹或夸张装饰。
- 构图应适合嵌入课程正文，在桌面宽屏和缩小后的页面中都能读清主流程。
- 普通概念图优先使用约 16:9；横向流程或左右对比可使用约 2.5:1。不要把多张图拼成一张 Montage。

文字要求：

- 图片文字使用英文，与英文 Course 正文术语保持一致。
- 标签短而明确，优先使用名词短语或动词短语，不在图中放长段落。
- 所有技术术语、大小写和拼写必须正确，例如 `APACHE DORIS`、`Frontend (FE)`、`Backend (BE)`、`CDC`、`SQL`。
- 不要出现乱码、伪文字、截断文字、重复标签或无意义小字。
- 不要在画面中加入图片编号、文件名、水印、页码或“Figure”字样。

三、画面组织原则

1. 流程图按照正文真实顺序组织，通常从左到右或从上到下。
2. Apache Doris 是课程主角时，应成为画面的视觉中心，但不能夸大成正文未表达的唯一组件。
3. 对比图使用清楚的左右分区或上下分区；两边使用相同的视觉尺度，便于直接比较。
4. 架构图明确区分客户端、协调/规划、执行、存储和结果，不要让箭头交叉或产生双重含义。
5. 数据组织图优先展示列、分片、分区、Tablet、节点或阶段之间的关系，而不是使用抽象装饰图形。
6. 可用一个短标题和一个短副标题说明图意，但正文已经明确时可以省略标题，把空间留给结构本身。
7. 每张图在缩小到课程正文宽度后，主要节点、方向和结论仍应一眼可辨。

四、图片文件与 Markdown 插入

1. 每张图片单独生成 PNG。
2. 保存在目标 Module 下：
   `assets/diagrams/`
3. 文件名采用两位数字排序和英文 kebab-case，例如：
   `01-ingestion-paths.png`
   `02-fe-be-query-flow.png`
4. 编号按照图片在 Course 中的出现顺序排列。
5. 使用相对路径插入 Markdown，例如：

   ![A client sends SQL to FE, which plans distributed work for BE nodes and returns the combined result.](assets/diagrams/02-fe-be-query-flow.png)

   *FE plans and coordinates the query while BE nodes execute the distributed work.*

6. Alt text 应客观描述图中关系，不能只写 `diagram`、`architecture` 或重复文件名。
7. 图片下方增加一句斜体英文说明，概括用户应该从图中理解的结论；不要把正文再复制一遍。
8. 图片一般放在相关概念已经由一到两个段落引入之后、下一个小节标题之前。不要把图片放在标题与第一段正文之间，除非它确实是整个小节的总览图。
9. 如果原文存在表达同一关系的 ASCII / text 流程图，可以用图片和一句说明替换该代码块；保留代码块前后的解释文字。
10. 如果原文没有 ASCII 图，只新增图片和说明，不删除或改写正文。
11. 不修改 Lab、Quiz、Notebook、课程逻辑或与目标 Course 无关的文件。
12. 不直接修改网站仓库中同步生成的 `apps/web/app/courses/content/` 副本；只修改课程源仓库中的 Markdown 和图片资源。

五、生成质量检查

每张图片生成后逐张检查：

- 背景是否为纯黑；
- 每个 Apache Doris 节点是否都是纯色深蓝块，并且只写 `APACHE DORIS`；
- 是否没有 Doris Logo、VeloDB Logo 或 `VELODB ENGINE`；
- 技术名称、箭头方向和因果关系是否与 Course 一致；
- 是否存在拼写错误、伪文字、重叠、裁切或难以辨认的小字；
- 是否保持统一的线宽、颜色、卡片形态和留白；
- 图片是否真正降低了该段内容的理解成本；
- Markdown 相对路径是否正确，文件是否实际存在；
- 图片顺序、文件编号、Alt text 和斜体说明是否相互对应。

不合格的图片应重新生成，不要用后期覆盖文字、拉伸图片或在 Markdown 中解释图片错误来补救。

六、最终交付

完成后给出：

1. 新增图片清单；
2. 每张图片插入的章节位置和教学作用；
3. 修改过的 Course Markdown 路径；
4. 明确说明是否替换了原有 ASCII / text 流程图；
5. 明确说明没有修改哪些相关文件，例如 Lab、Quiz 和其他 Module。
```

## 单张图片生成时可追加的提示模板

当图片生成工具需要逐张调用时，在上面的统一要求后追加：

```text
本次只生成第 <N> 张图片，不要生成拼图或多版本合集。

教学目标：
<THIS_IMAGE_LEARNING_GOAL>

画面结构：
<COMPONENTS_AND_FLOW>

必须出现的英文标签：
<REQUIRED_LABELS>

不得出现的内容：
<FORBIDDEN_OR_UNSUPPORTED_ELEMENTS>

输出比例：
<16:9_OR_WIDE>

再次强调：纯黑背景；所有 Apache Doris 节点均为纯色深蓝矩形块，块内只写 `APACHE DORIS`，不放 Logo；其余组件保持 VeloDB Website 深色技术流程图风格。
```

## 使用说明

- `<COURSE_MD_PATH>` 必须替换为课程源仓库中的真实 Markdown 路径。
- `<MODULE_ID>` 建议填写课程名、Level 和 Module，例如 `real-time-analytics / level-2 / module-4`。
- 如果只需要分析配图位置而暂时不生成图片，应把任务范围明确改为“只输出选点计划，不修改文件”。
- 如果已经确认选点，可以直接提供每张图的教学目标和组件关系，从生成阶段开始执行。
